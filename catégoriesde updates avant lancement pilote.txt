	Architecture & Sécurité
Migration vers l'architecture MVC complète

Séparation des privilèges — AdminController isolé
Aucune méthode admin partagée avec les controllers publics. Toute action admin est loggée (non-répudiation).

Authentification bcrypt + sessions Streamlit sécurisées
Seul le minimum nécessaire est stocké en session (jamais le hash). Méthodes statiques hash_password / verify_password.

Permissions granulaires par domaine
Remplacement d'expert_topics (liste simple) par domain_permissions (learner / contributor / expert par catégorie). Migration automatique au login.

Guard de rôle sur toutes les vues sensibles
st.stop() immédiat si le rôle ne correspond pas. Contributeur, validateur et admin ont chacun leur garde en entrée.

Mode survie MongoDB (survival_kit.json)
Si MongoDB est indisponible, l'app reste accessible avec les FAQ statiques et liens d'urgence. db_instance.is_alive() vérifié au démarrage.

Correction bug _log_query (TypeError float slicing)
str(r)[:200] et float(sc) pour normaliser les types numpy de PyTorch. try/except pour ne jamais crasher le chat à cause du log.

Correction bug ObjectId comme clé Streamlit
str(item['_id']) systématique dans toutes les vues pour éviter l'erreur de type sur les widgets Streamlit.

Anonymisation pré-envoi : Créer une fonction de nettoyage des données personnelles (noms, emails) avant traitement par l'IA.

Migration vers FastAPI : Déporter la logique métier (Auth, CRUD) vers des API endpoints.

Validation via Pydantic : Créer des modèles de données pour valider chaque entrée/sortie API.


	Moteur NLP & recherche
Cache NLP avec @st.cache_resource
Le modèle all-MiniLM-L6-v2 (~90 Mo) est chargé une seule fois via get_nlp_engine(). Sans ce cache, Streamlit rechargeait le modèle à chaque rerun.

Catégorisation automatique des questions NLP
classify_category() combine mots-clés (fast path) + similarité sémantique sur des phrases d'ancrage. Chaque ticket créé a une catégorie pertinente.

Scoring d'intention HOT / WARM / COLD
classify_intent() analyse les mots-clés de la question. Alimente le compteur de déclenchement RG-05.

Alerte expert ciblée par domaine (RG-03)
Requête MongoDB sur expert_topics + domain_permissions. Fallback sur tous les validateurs si aucun expert ciblé trouvé.

Traitement différencié expert_suggestion
Quand un expert pose une question dans son propre domaine, le ticket est marqué expert_suggestion — pas d'alerte externe, visible dans le dashboard admin

Normalisation des catégories (casse + synonymes)
normalize_category() rend "inscription", "INSCRIPTIONS", "candidature" équivalents → "Admission". Élimine les doublons de catégories en base.

	Base de connaissances & workflow
Workflow de validation complet à 4 niveaux :Question → ticket → proposition contributeur → certification validateur → notification étudiant. Chaque étape est tracée en base.

Recatégorisation des questions par le contributeur
Selectbox + bouton dans chaque question. kb_controller.recategorize() normalise et enregistre avec recategorized_by / recategorized_at.

Filtres et recherche dans les espaces contribuer et valider
Trois filtres combinables : catégorie, état de proposition, mot-clé. Identiques aux filtres de la v2 d'origine.

Actualisation automatique après chaque action
st.rerun() systématique après validation, certification, archivage, recatégorisation, suppression, création d'utilisateur.

Invalidation des réponses certifiées
Bouton "Invalider" dans l'onglet Validées. Remet la contribution en statut en_attente pour correction.

Notification étudiant à la certification
Après update_contribution(), send_answer_to_student() est appelé si user_email est connu (pas anonyme). Email HTML avec la réponse certifiée.

Bouton "Proposer" conditionnel selon le niveau du domaine
Dans validator_view, le bouton affiché dépend du niveau dans le domaine : "Certifier" pour expert, "Proposer" pour contributor, lecture seule pour learner.
